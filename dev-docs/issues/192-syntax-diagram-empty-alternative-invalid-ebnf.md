## Description

Any grammar containing an alternative with an empty right-hand side makes
`plcc-diagram` write a malformed `@startebnf` block, and `syntax.png` comes back
as PlantUML's error image — the words **"Syntax error!"** — instead of a
diagram.

[`syntax_diagram/plantuml/emit.py`](../../src/plcc/diagram/syntax_diagram/plantuml/emit.py)
renders an empty production as the empty string and joins alternatives with
`' | '`, so a rule with an empty alternative comes out as:

```
ListTail = 'COMMA', 'NUM', ListTail |  ;
```

PlantUML's EBNF parser rejects the dangling alternative. It has no notation for
an empty alternative at all, so emitting one as the empty string cannot work —
the language has to be expressed with optionality instead.

`plcc-diagram` exits **0** and prints the output path as if it had succeeded,
so nothing signals a problem until a human opens the PNG. The class diagram
generated by the same run is correct and unaffected.

**This is not an edge case.** Recursion with an empty alternative is the
standard way to write a list in an LL(1) grammar; it is the form used by the
comma-separated-numbers example in the course textbook's *Syntax* chapter; and
it is what plcc-ng's own LL(1) conflict message instructs the user to write:

```
  Tip: left-factor the common prefix:
    <List> ::= <NUM> <ListTail>
    <ListTail> ::= COMMA <List>
    <ListTail> ::=    (empty)
```

So a user who follows that tip to fix one problem lands on this one. Grammars
written with `**=` instead are unaffected and render correctly.

Two existing unit tests pin the broken output, so the fix has to update them:

- `test_empty_production` asserts `'Opt =  ;' in result`
- `test_arith_grammar_smoke` asserts `"ExprRest = 'PLUS', Term, ExprRest |  ;" in result`

The shape was specified this way from the start — the same two assertions appear
in [`2026-06-25-syntactic-ebnf-diagram.md`](../plans/2026-06-25-syntactic-ebnf-diagram.md),
the plan the emitter was built from. It was never a regression; the empty case
was simply not rendered before it was pinned.

## Steps to Reproduce

Save as `spec.plcc` — this is the textbook's comma-separated-numbers grammar,
unmodified:

```
skip  WHITESPACE '\s+'
token NUM        '\d+'
token COMMA      ','

%

<List>          ::= <NUM> <ListTail>
<ListTail:Some> ::= COMMA <NUM> <ListTail>
<ListTail:Zero> ::=
```

```console
$ plcc-diagram -s spec.plcc
plcc-ng/diagram/class.png
plcc-ng/diagram/syntax.png
$ echo $?
0
$ cat plcc-ng/diagram/syntax.puml
@startebnf
List = 'NUM', ListTail ;
ListTail = 'COMMA', 'NUM', ListTail |  ;
@endebnf
```

`plcc-ng/diagram/syntax.png` renders as *"Syntax error!"* above a partial
diagram containing only `List`. `class.png` from the same run is correct.

Measured on plcc-ng 2.0.2.

**The degenerate case reproduces too, and is reachable.** A non-terminal whose
only production is empty is accepted by `plcc-parse`:

```
skip WS '\s+'
token NUM '\d+'

%

<Top> ::= <NUM> <Opt>
<Opt> ::=
```

```console
$ echo "5" | plcc-parse -s spec.plcc
Top
  NUM '5' [-:1:1]
  Opt (empty)
```

and emits `Opt =  ;`, which PlantUML also rejects. So the fix needs to handle
both "some alternatives are empty" and "all of them are".

## Notes

**Suggested fix**, in `_render_alternatives`: drop the empty alternatives and
wrap what remains in PlantUML's optional brackets, which expresses the same
language. When *every* alternative is empty, emit an empty terminal `''`, which
PlantUML draws as an empty box.

Rendered against `plantuml.com` to confirm, rather than reasoned about:

| emitted | renders as |
|---|---|
| `ListTail = 'COMMA', 'NUM', ListTail \|  ;` | **"Syntax error!"** |
| `ListTail = [ 'COMMA', 'NUM', ListTail ] ;` | the rule, with a bypass line over it |
| `A = [ 'X' \| 'Y' ] ;` | a choice of `X` or `Y`, with a bypass |
| `Opt = [ ] ;` | **"Syntax error!"** — so this is not the answer for the degenerate case |
| `Opt = '' ;` | an empty box |

The bypass is the correct picture: it is exactly what "or nothing" means in a
railroad diagram.

**Secondary suggestion, separable from the fix.** The renderer returns HTTP 200
with an error image, so
[`plantuml/build.py`](../../src/plcc/diagram/plantuml/build.py) currently cannot
tell success from failure and `plcc-diagram` reports success either way. A check
for PlantUML's error signature would turn a silently wrong PNG into a message.
Left out of the fix here because it is a different concern and wants its own
decision.

**Reported from downstream.** Found while building a parser sandbox for a
programming-languages course — students were going to be told to run
`plcc-diagram` on the chapter's own example. The reproduction above is
self-contained and was rebuilt against plcc-ng alone.
